2. **`backup-app.sh` reported success for a backup with no data** (fixed).

   - Checked for real: prefix 13041 now fetches, loads and builds (291 parcels, 0 condo rows).
   - Full-county runs are unaffected: `db validate` still requires every typed table to be non-empty.
5. **The first `scripts/check.sh` on a fresh clone hung for 11 minutes.**
   - `go test` in `internal/web`, `tools/prcheck` and `tools/prloc` hit Go's 10-minute timeout. Those are pure unit tests in the two tools.
   - A rerun passed in 7 s, and I couldn't reproduce it reliably. *(One of my own gate runs hung the same way; see "Gate hang" below.)*

- **Not established:** no goroutine dump came through, and `lsof` and `ps` were unavailable to the session. A shorter `go test -timeout` (proposal 3 below) would at least turn a stall into a fast failure with a dump.
- On an idle run, `internal/e2e` adds about 3 s.

## Proposed CI and deploy changes

1. **Nightly fuzzing:** `.github/workflows-pending/fuzz.yml` runs each target for 3 minutes and uploads any crasher. The README there covers it.
2. **e2e in CI:** nothing to do. `internal/e2e` is an ordinary package, so `scripts/check.sh`, and with it CI, runs it.
3. **A test timeout in `scripts/check.sh`,** e.g. `go test -timeout 5m`, so a hang fails in minutes, not 10+. This is a one-line change to a file the parallel test run may touch, so it's proposed, not made.
4. **`deploy.sh`:**
   - validate the Caddyfile before installing it;
   - keep the previous binary;
   - after the healthz curl, run `scripts/smoke.sh https://assessgap.com` locally and print the result. Make it a warning at first, while production catches up with `main`; finding 1 would trip it today with `SMOKE_STRICT=1`.
5. **HSTS** in the Caddyfile.
6. **Server prerequisites and the restore procedure** written down (a short `ops/README.md`), including that the backup copy is in WAL mode and that a stale `app.db-wal`/`-shm` must be removed before copying a backup into place.

## Open questions

1. **Deploy `main`?** Production's report numbers differ from `main`'s (finding 1). That's the maintainer's call, and it should be deliberate: the 2026-11-26 tune changes every report.
2. **Full-database performance is unmeasured.** This session couldn't read `cook-c.db`. Rerun the 50-PIN p50/p95 on the full database; the web agent's scripts in its scratch dir did exactly that on the fixture.
3. **Should report pages be indexable?** In production they have no `noindex`, and their titles are home addresses.
4. **The `"verdict"` field name in `check -json`:** rename it (a breaking change for `ops/refresh.sh` and any scripts), or accept it as machine output?
5. **`build.sql` hardening** against non-numeric or missing values (fuzz results): worth a deliberate PR?
6. **`db *` and `$ASSESSGAP_DB`:** should `db build`, `db validate` and `db finalize` honour it as the README implies, or should the README say they don't?
