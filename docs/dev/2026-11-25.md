## B. One `assessgap` command

`cmd/assessgap` is a thin `main` around `internal/cli`. The dispatcher uses the standard library `flag` package. Flags may come before, between or after positional arguments, and `--` ends flag parsing.

| Command | What |
|---|---|
| `check [-db] [-year] [-json] [-brief] [-live] <address-or-PIN>` | Terminal report: address, township window, this home vs the median AV/sq ft, gap, how many similar homes are assessed lower, the lower-assessed homes with PINs, neighborhood BOR outcomes, data checks. `-json` prints the full report. An address that matches several homes lists them and exits 1. A full address picks its exact match over unit addresses. |
| `report [-db] [-year] [-live] -o out.pdf <address-or-PIN>` | The evidence report PDF |
| `township [-on DATE] [name]` | Filing window for one township (names are forgiving: "lakeview", "new trier township"), or a table of all 38 |
| `db sync\|fetch\|load\|build\|validate\|finalize` | `sync` = the old `ingest all` + `build`. `validate` and `finalize` are the old `refresh` steps. |
| `serve` | The website (`-db`, with `-cook` kept as an alias) |
| `backtest`, `sample` | The old `compseval`, opening the database read-only |
| `live-eval` | Live mode vs a full local database (Task C) |

## C. Live mode: no local database

**How it works** (`internal/live`): three rounds of parallel Socrata queries for one PIN.

1. The subject's assessed values (`pin = X`), which give its latest year and neighborhood.
2. All assessed values for that neighborhood and year (`year = Y AND nbhd = N`), plus the neighborhood's parcel rows (`nbhd_code = N OR pin = X`).
3. The datasets that have no neighborhood column, fetched by the 7-digit PIN blocks seen in round 2 (`starts_with(pin, '1328100') OR …`, at most 150 blocks per request): addresses, residential characteristics and BOR appeals. Plus the subject's own sales, condo and Assessor-appeal rows.

Every query uses `$select` for only the columns `build.sql` reads. Pages go through the same `socrata.Client`, `store.LoadRaw` and `build.sql` as a full build, into an in-memory SQLite database. The `comps` engine runs on it unchanged.

**Measured** with `assessgap live-eval -n 200 -seed 1` against the full read-only database. That run checked 200 random supported homes, stratified round-robin across all **38 townships**, sequentially, unauthenticated (no app token), from one machine on 2026-11-24.

| Measure | Result |
|---|---|
| Identical reports (subject, statistics, comparable PINs in order, every comparable's details, lower-assessed PINs, neighborhood BOR stats, tier, sales) | **200 / 200 (100%)** |
| Mismatches | none, so no causes to report |
| API requests per check | p50 9, p95 12, max 18 |
| Data per check | p50 2.3 MB, p95 8.4 MB, max 15.4 MB |
| Wall time per check | **p50 1.5 s, p95 3.0 s**, max 6.2 s |
| Rate limiting | none: 0 retries and 0 HTTP errors over roughly 1,900 requests in under 6 minutes |
| Largest neighborhood (72380, Lake, 12,457 supported homes) | 18 requests, 12.1 MB, 6.8 s for one live check (timing only, not compared) |

It clears the bar (≥99% match, p95 < 15 s), so it is wired in:

- `check` and `report` take `-live`.
- When no database is asked for (no `-db`, no `$ASSESSGAP_DB`) and none exists at `./data/cook.db`, a PIN is checked live.
- Searching by address still needs a local database. The error says so and explains how to build one.
- `internal/live` has offline unit tests, plus a test that `build.sql` runs on empty live tables (so the column lists cover what the build reads).
- A real-API test skips without network, under `-short`, and when `$CI` is set, so CI stays independent of the county's servers.

Caveats:

- The neighborhood appeal statistics use the last three tax years present in the fetched rows, while a full build uses the last three in the whole county. They agree unless a neighborhood has no appeals at all in the latest year. That never happened in the sample, but it is possible.
- These timings are for one user. A public website on live mode would multiply county API traffic; it should keep a local database or use an app token and caching.

## D. Data inventory

`docs/data-inventory.md` covers:

- every column of the 8 ingested datasets: portal description, type, fill rate and distinct count for supported homes in the latest year (computed read-only on the full database), and engine use;
- the current county datasets worth adding;
- a config proposal.

Highlights:

- The engine uses 11 characteristics.
- About 18 residential characteristics are ≥99% filled with real variety and could be offered as choices, including bedrooms, rooms, basement finish, garage size, central air, attic, fireplaces and porch.
- Seven are effectively constant (construction quality, repair condition, CDU and others), and renovation is 1.2% filled.
- The parcel universe already carries strong location fields we don't load: coordinates, census tract and block group, subdivision ID, school districts.
- Parcel Proximity (`ydue-e5u3`) adds each parcel's three nearest neighbors and distances to transit, roads and water.
- The proposal is a list of criteria (field, rule, tolerance per widening step, weight) whose default reproduces today's rules exactly, testable with the backtest and `live-eval`. It keeps the neighborhood and tax-year pool, and keeps building sq ft required.
